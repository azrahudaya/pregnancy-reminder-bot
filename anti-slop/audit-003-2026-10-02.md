## HIGH

**1. Jawaban validasi persalinan dengan tanda baca akhir ditolak.**
Lokasi: index.js:1402 dan index.js:1405 (regex `^(sudah|udah|ya|iya|yes|benar)$` tanpa membuang tanda baca).
Bukti: uji pada salinan DB, stage poll persalinan aktif: `"Ya"` -> lanjut ke pertanyaan tanggal lahir, `"Ya."` -> `"Aku belum paham pesan itu..."`, `"Sudah."` -> `"Belum ada pertanyaan aktif hari ini..."`.
Dampak: ibu yang baru melahirkan dan menulis dengan titik tidak dipandu mengisi tanggal lahir, jadwal kunjungan nifas tidak dibuat. Ini fase paling kritis.
Usul: buang tanda baca akhir sebelum mencocokkan (`replace(/[.!]+$/, "")`).
Aturan terkait: R-27 (state jalan buntu), C-4.

**2. Untuk user yang dibuat lewat `admin allow`, perintah `start` melompat ke pertanyaan jam dan melewati 8 pertanyaan lain.**
Lokasi: index.js:5919-5927 (cabang `if (!user.reminder_time)` menyetel `onboarding_step: 9` lalu mengirim `QUESTIONS[8].text`).
Bukti: baris user dengan status onboarding dan step 1, kirim `start` -> langsung pertanyaan jam pengingat, baris berubah `onboarding_step=9`; setelah dijawab status jadi `active` dengan `name`, `age`, `hpht` tetap null.
Dampak: profil kehamilan kosong tapi user dianggap aktif dan diingatkan harian; tanpa HPHT, logika HPL dan deteksi persalinan tidak pernah jalan. Ini persis alur yang saya anjurkan di panel ("minta dia kirim pesan ke bot"), jadi instruksi itu harus ikut diperbaiki.
Usul: pada cabang `start`, bila `name` atau `hpht` kosong, reset ke `onboarding_step=1` dan kirim Q1.

**3. `parseYesNo` mengecek kata positif lebih dulu, sehingga jawaban negatif yang memuat "ya" tercatat sebagai "ya".**
Lokasi: index.js:3686-3691.
Bukti: `"belum ya" -> true`, `"tidak ya" -> true`, `"tidak boleh" -> true`; sedangkan `"engga"` dan `"blm"` -> null (tidak dikenali). Uji alur nyata: pertanyaan "Apakah rutin mengkonsumsi obat?" dijawab `"belum ya"` dan tersimpan `routine_meds=1`.
Dampak: data kesehatan (kepatuhan obat, konsumsi teh, izin diingatkan) bisa tersimpan terbalik, dan jawaban umum seperti "engga" membuat ibu diulang terus.
Usul: cek pola negatif lebih dulu dan tambahkan `engga`, `blm`, `gak`.

**4. Tidak ada jalur pemberitahuan manusia saat bot mati, sesi putus, atau DB rusak.**
Lokasi: index.js:6778 (`sendAlert` hanya `console.error` + POST opsional ke `ALERT_WEBHOOK_URL`).
Bukti: `grep -c ALERT_WEBHOOK_URL /opt/remindcare/.env` -> 0. `ADMIN_WA_IDS` hanya dipakai untuk flag admin (index.js:50, 6063), bukan tujuan alarm. Jejak `ALARM [sesi-putus]` dan `[auth-gagal]` hanya ada di journal.
Dampak: bot bisa diam berjam-jam tanpa ada yang tahu, padahal ini layanan pengingat obat untuk ibu hamil.
Usul: kirim alarm ke admin WhatsApp (`ADMIN_WA_IDS`) atau pasang `ALERT_WEBHOOK_URL` ke kanal yang benar-benar dipantau.

**5. Balasan pesan media menembus gerbang allowlist dan gerbang blokir.**
Lokasi: index.js:6041-6047 (cabang "belum bisa membaca pesan suara atau gambar" berada sebelum cek rate limit, allowlist, dan `is_blocked`).
Bukti: dengan `ENFORCE_ALLOWLIST=1`: nomor asing kirim teks -> `"Nomor ini belum diizinkan"` (benar), nomor asing kirim media -> dibalas `"Aku belum bisa membaca pesan suara atau gambar..."`; nomor yang diblokir kirim media -> juga dibalas, padahal pesan teks dari nomor yang sama diabaikan senyap.
Dampak: nomor asing dan nomor yang sudah meminta berhenti tetap memancing balasan dari nomor WhatsApp live, bertentangan dengan kebijakan anti-broadcast sekaligus memperbesar risiko pembatasan nomor.
Usul: pindahkan cabang media ke setelah gerbang allowlist dan `is_blocked`.

**6. Sandbox Chromium dimatikan padahal proses bukan root.**
Lokasi: index.js:7617 (`--no-sandbox --disable-setuid-sandbox` bila `PUPPETEER_NO_SANDBOX=1`), index.js:7611-7615.
Bukti: `grep -cE "^PUPPETEER_NO_SANDBOX=1" /opt/remindcare/.env` -> 1; proses berjalan sebagai user `remindcare` (uid non-root).
Dampak: WhatsApp Web (konten pihak ketiga) dirender tanpa sandbox di host yang sama dengan DB data kesehatan. Sandbox hanya wajib saat proses root; di sini murni mengurangi pertahanan.
Usul: hapus `PUPPETEER_NO_SANDBOX` di .env, biarkan sandbox aktif.

**7. Satu host menampung bot dan aplikasi lain yang terbuka ke internet (port 80/443 tembus ufw).**
Lokasi: host 213.163.192.71; `ufw status` hanya `22/tcp ALLOW`, tetapi `iptables -t nat -L DOCKER` meneruskan 80 dan 443 ke container `steto-caddy-1`.
Bukti: dari luar, `curl -o /dev/null -w "%{http_code}" http://213.163.192.71/` -> 308 (hidup). Kontainer lain: 7 buah (web, api, worker, postgres, caddy, dll).
Dampak: asumsi "cuma port 22 yang terbuka" tidak berlaku. Bot berbagi kernel, disk, dan CPU dengan stak lain; kompromi salah satu aplikasi bisa menyentuh host tempat DB ibu hamil disimpan.
Usul: batasi publikasi port lewat rantai `DOCKER-USER` atau pindahkan bot ke VPS terpisah, lalu verifikasi ulang dari internet.

## MEDIUM

**8. `admin allow 08xx` dan `ALLOWLIST_WA_IDS` bentuk 08xx tidak pernah cocok dengan pengirim nyata.**
Lokasi: index.js:471-475 (`normalizeWaIdInput` hanya membuang non-digit, awalan 0 tidak diubah ke 62).
Bukti: `normalizeWaIdInput("08123456789")` -> `"08123456789@c.us"`, sedangkan pengirim selalu `628...@c.us`; `admin allow 081234500099` -> `"OK allow 081234500099@c.us. Nomor masuk daftar akses."` untuk identitas yang tidak akan pernah muncul.
Dampak: operator mengira sudah memberi akses, ibu tetap ditolak "Nomor ini belum diizinkan". Panel sudah benar (`normalizeOperatorNumber` mengubah 0 menjadi 62), jadi dua jalur ini berbeda hasil.
Usul: pakai `normalizeOperatorNumber` di `normalizeWaIdInput`.

**9. `admin unblock` tidak mengaktifkan ulang layanan.**
Lokasi: index.js:4400-4402 (hanya `is_blocked: 0`) vs aksi panel index.js:6585-6592 (juga `allow_remindcare: 1`, `status: active`).
Bukti: `admin unblock` -> baris jadi `is_blocked=0, status=paused, allow_remindcare=0`; lewat panel -> `status=active, allow_remindcare=1`.
Dampak: ibu yang dibuka blokirnya tetap tidak menerima pengingat, tanpa pesan galat apa pun.
Usul: samakan perilaku `unblock` in-band dengan aksi panel.

**10. Tombol Cabut di panel tidak mencabut apa pun bila nomornya juga terdaftar di .env.**
Lokasi: index.js:7120 (`fromEnv`) dan index.js:7143-7148.
Bukti: nomor yang ada di `ALLOWLIST_WA_IDS` -> respons `{from_env: true, revoked: false}`, baris user tetap `is_allowed=1, status=active`.
Dampak: operator melihat baris hilang dari tabel dan mengira akses sudah dicabut. Pesan status sebenarnya sudah menyebut "masih ada di berkas .env", tapi mudah terlewat.
Usul: jangan tampilkan tombol Cabut untuk baris berkas .env, ganti dengan keterangan cara mencabutnya.

**11. `admin allow` menerima string apa pun yang mengandung "@", termasuk alamat @lid, dan entri itu tidak bisa dihapus dari panel.**
Lokasi: index.js:468-470 (`if (trimmed.includes("@")) return trimmed`), tombol hapus panel memakai `normalizeOperatorNumber` (index.js:571-581) yang mengubah `@lid` menjadi `<digit>@c.us`.
Bukti: `admin allow 204930287689898@lid` -> "OK allow 204930287689898@lid."; menghapus entri yang sama dari panel mengarah ke `204930287689898@c.us` yang tidak ada di daftar.
Dampak: entri nyasar menetap di daftar akses tanpa cara membersihkan dari panel.
Usul: tolak input non-`@c.us` pada `admin allow`, dan dukung hapus `@lid` apa adanya.

**12. Copy menjanjikan pengingat harian, tetapi satu hari dalam sepekan dilewati.**
Lokasi: index.js:6645 (`reminder_skip_weekday` fallback 7) dan pesan konfirmasi onboarding.
Bukti: uji tick pada salinan DB, Sabtu kirim, Minggu tidak kirim (`last_reminder_date` terisi, tidak ada pesan). Pesan yang diterima user: "RemindCare akan mengingatkan setiap hari jam 19:00 WIB."
Dampak: ibu merasa sistemnya lupa, padahal disengaja sebagai penangkal pola otomatis.
Usul: perbaiki copy (sebut hari jeda) atau setel `reminder_skip_weekday=-1` bila memang ingin harian.

**13. Rotasi password admin tidak mencabut sesi yang sedang aktif.**
Lokasi: scripts/rotate-admin-password.js:62-72 (hanya mengubah hash di tabel settings), sesi disimpan in-memory di index.js:145 dan hanya dihapus saat logout atau kedaluwarsa.
Bukti: setelah hash diganti, sesi lama tetap valid sampai TTL habis (default 8 jam, `ADMIN_WEB_SESSION_TTL_MS` tidak diset di .env).
Dampak: pergantian password karena diduga bocor tidak memutus akses penyerang yang sudah memegang cookie.
Usul: tambah aksi "cabut semua sesi" di panel atau `adminSessions.clear()` pada proses yang berjalan.

**14. Sesi admin tidak diikat ke IP atau User-Agent dan tanpa timeout idle.**
Lokasi: index.js:1920-1935 (`getAdminSession` hanya memeriksa token dan `expiresAt`).
Dampak: cookie yang dicuri bisa dipakai dari mana saja sampai 8 jam.
Usul: simpan IP + UA saat login, tolak bila tidak cocok, dan tambahkan timeout idle.

**15. Cookie sesi tanpa flag Secure dan HSTS mati.**
Lokasi: index.js:1952 (`Secure` hanya bila `ADMIN_WEB_COOKIE_SECURE`), index.js:6849-6851 (HSTS ikut flag yang sama). Bukti: `ADMIN_WEB_COOKIE_SECURE=0` di .env.
Dampak: saat ini akses hanya lewat 127.0.0.1 atau terowongan SSH sehingga dampaknya kecil, tetapi konfigurasi ini jadi bahaya begitu panel dipasang di balik proxy TLS.
Usul: setel `ADMIN_WEB_COOKIE_SECURE=1` saat sudah ada TLS.

**16. Password admin punya salinan plaintext di disk dan masih ada jalur verifikasi plaintext.**
Lokasi: index.js:1755-1758 (menulis berkas), index.js:1771-1795 (membaca), index.js:1854 (fallback `isPasswordMatch(input, passwordConfig.password)`).
Bukti: `/opt/remindcare/data/admin_web_password.txt` ada (mode 600, 27 byte). Hash scrypt memang sudah ada di tabel settings (`admin_password_hash` 64 karakter + salt 32 karakter), jadi berkas plaintext itu cadangan yang tidak perlu.
Dampak: satu kebocoran disk atau backup langsung membuka panel.
Usul: hapus berkas plaintext dan hapus fallback-nya, jadikan hash DB satu-satunya sumber.

**17. Tiga peta di memori tumbuh tanpa batas.**
Lokasi: index.js:140 `lastAckByMessageId` (hanya ditulis di index.js:7727, tidak pernah dibaca), index.js:141 `adminLoginAttempts` (hanya dihapus saat login sukses), index.js:144 `rateLimitState` (tidak pernah dihapus).
Bukti: `grep -n "lastAckByMessageId|rateLimitState|adminLoginAttempts"` menunjukkan tidak ada `.delete()` untuk dua yang pertama dan satu untuk yang kedua hanya pada jalur sukses. `checkRateLimit` dipanggil sebelum gerbang allowlist (index.js:5729), jadi nomor asing pun membuat entri.
Dampak: RAM naik terus sepanjang umur proses; percobaan login dari banyak IP bisa dipakai menekan memori.
Usul: hapus peta yang tidak terpakai, beri cap ukuran + penyapuan berkala untuk dua lainnya.

**18. Tidak ada penanganan `unhandledRejection` / `uncaughtException`, dan `main().catch` tidak keluar.**
Lokasi: index.js:7751-7753 (hanya `console.error` tanpa `process.exit`).
Bukti: `grep -nE "unhandledRejection|uncaughtException" index.js` -> tidak ada hasil. Handler SIGINT/SIGTERM baru terpasang setelah `main` berhasil.
Dampak: kegagalan dini tidak tereksekusi shutdown rapi (DB dan sesi WhatsApp berisiko kotor); restart bergantung pada `Restart=always`.
Usul: pasang handler global yang log, kirim alarm, lalu keluar dengan kode non-zero terkontrol.

**19. Jalur berisiko tanpa tes sama sekali.**

Usul: tambah tes minimal untuk ekspor CSV, `handleAdminCommand` allow/block, dan lock.

**20. Selektor pemilih tombol di halaman pengaturan salah, jadi penguncian tombol darurat tidak pernah jalan.**

Dampak: operator bisa memicu pause, resume, perawatan, dan simulasi berturut-turut atau bersamaan.

Aturan terkait: R-26, C-2, R-35.

**21. `aria-busy` tidak pernah dimatikan pada tabel User dan Catatan pengingat.**

Dampak: pembaca layar mengumumkan area itu sebagai terus memuat walau data sudah ada.

**22. Halaman detail user tidak punya satu pun tombol aksi, padahal backend mendukungnya.**

**24. Backup hanya ada di VPS yang sama, tanpa enkripsi, tanpa uji restore.**

**25. Journal systemd tidak persisten, tanpa batas ukuran, dan fail2ban tidak aktif.**

**26. Patch keamanan sistem tertunda dan reboot tertunda sejak 27 September.**

**27. Dependency produksi: 16 kerentanan, 1 critical.**
Lokasi: package.json:26-33. Bukti: `npm audit --omit=dev` -> 16 (2 low, 13 high, 1 critical); jalur utamanya `sqlite3 -> node-gyp -> tar <=7.5.20` (critical, path traversal dan DoS) dan `whatsapp-web.js -> puppeteer -> extract-zip` (high). `npm outdated`: express 4.22.3 (terbaru 5.2.1), sqlite3 5.1.7 (terbaru 6.0.1).

Usul: uji upgrade sqlite3 dan whatsapp-web.js di `/opt/remindcare/deploy-staging` sebelum ke produksi.

## LOW

**28. Fitur koreksi salah-tap tidak bisa ditemukan user.**

**29. `POST /admin/login` tanpa perlindungan CSRF, dan perbandingan token CSRF tidak constant-time.**

## Area yang sudah dicek dan bersih

- SQL injection: tidak ada. 85 pemanggilan `dbRun/dbGet/dbAll` memakai placeholder; interpolasi hanya dari daftar kolom internal dan rangkaian `?`.
- XSS: tidak ada. Nilai dari DB dan URL masuk lewat `textContent`/`createElement`, bukan `innerHTML`; nilai di blok script divalidasi regex dan di-escape. Uji nyata `escapeForScriptContext("</script><img src=x onerror=alert(1)>")` menghasilkan bentuk ter-escape.
- CSP nonce per respons, `X-Frame-Options`, `nosniff`, `Referrer-Policy`, `Permissions-Policy` aktif (index.js:6825-6847).
- Otorisasi: tidak ada route pengubah state tanpa `requireAdmin` + `requireCsrf` kecuali `/admin/login`; tidak ada GET yang mengubah state; perintah admin WhatsApp diverifikasi dari `is_admin` di DB.
- Rahasia: `.env` dan `data/` ter-gitignore, izin 600 dan 700, tidak ada rahasia ter-commit, tidak ada password yang ditulis ke log.
- Data produksi: integrity ok, tidak ada log ganda per user per hari, tidak ada user aktif tanpa jam pengingat, tidak ada alias yang menunjuk dirinya sendiri atau ke user yang tidak ada, indeks loop pengingat benar-benar dipakai.

- Tanpa em dash: 0 karakter U+2014 di index.js, lib, dan keempat halaman ter-render.
- Ketahanan yang terbukti benar di uji: dedupe pesan masuk, rate limit per user, tidak ada pengingat ganda sehari, jendela basi 30 menit, parser HPHT menolak tanggal mustahil dan masa depan, user diblokir senyap untuk teks, gerbang non-admin.
